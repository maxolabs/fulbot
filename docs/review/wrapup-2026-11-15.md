## How to test SQL without disturbing the other tracks

Write `supabase/tests/<track>.sql` as a scenario script with no `BEGIN`/`COMMIT` of its own.
Assertions raise an exception on failure (`DO $$ … RAISE EXCEPTION … $$`). Run your migration
and the scenarios in one transaction that is always rolled back:

```sh
DB=postgresql://postgres:postgres@127.0.0.1:56622/postgres
{ echo "BEGIN; SET LOCAL lock_timeout = '30s';"; cat supabase/migrations/<yours>.sql supabase/tests/<track>.sql; echo "ROLLBACK;"; } \
  | psql "$DB" -v ON_ERROR_STOP=1 -q
```

DDL is transactional, so nothing persists and other tracks are only blocked for the few
seconds the script holds its locks. Act as a user inside the script with
`SET LOCAL role authenticated; SELECT set_config('request.jwt.claims', json_build_object('sub', '<uuid>', 'role', 'authenticated')::text, true);`
and `RESET role;` to go back to postgres. Keep the file: it is a deliverable, and the
orchestrator reruns all four on the integrated DB.

When your SQL tests pass and you need the UI, you may apply your migration to the shared DB
for real (`psql "$DB" -v ON_ERROR_STOP=1 -f <migration>`); that is why it must be idempotent.
Never run `supabase db reset`, `supabase stop` or `supabase start`, and never drop the seed.

## Rules for every track

1. Work only in your worktree. Never push. Never touch another track's worktree or branch.
2. Commit early (WIP) and after each milestone; the final commit and the report are part of
   the task.
3. No background processes for work you must wait for: run everything in the foreground with
   a timeout. Only exception: your own `next dev` server, which you start with
   `run_in_background` and stop with `pkill -f "next dev -p <your port>"` (exact port, never a
   generic `pkill -f node`).
4. Gates before you report: `npm run type-check`, `npm run lint`, `npm test`, your SQL
   scenario file, and `npm run build` (env from `app.env` plus `NEXT_PUBLIC_APP_URL`).
   Run the build last; four builds at once overload the machine.
5. Every touched screen: screenshots at both sizes, light, plus dark for at least one
   screen. Look at them yourself and list the PNG paths in the report.
6. User-facing text is Spanish (vos register) in `es.json` and English in `en.json`. Follow
   `docs/ui-rework/06-principles.md` (tokens only, rows over cards, one orange per screen,
   no `dark:` classes).
7. Report: what you built per decision, the SQL objects you redefined, anything you need from
   another track, gate results with numbers, and screenshot paths.
