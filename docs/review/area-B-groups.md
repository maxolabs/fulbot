## 0. Role model — what is actually enforced

### 0.1 Data model
- `group_role` enum: `admin | captain | member` (`supabase/migrations/00001_initial_schema.sql:12`).
- `group_memberships (id, group_id, player_id, role default 'member', is_active default true, joined_at)`, `UNIQUE(group_id, player_id)` (`00001:90-99`). Membership is keyed on **player_profiles.id**, not `users.id`.
- One `player_profiles` row per user, auto-created by the auth trigger `handle_new_user()` (`00002_auth_triggers.sql:4-33`) with `display_name` from `raw_user_meta_data.name` or the e-mail local part. Every stat column (`matches_played, goals, assists, mvp_count, clean_sheets, reliability_score, overall_rating`) lives on this single **global** profile row — there is no per-group stat table.
- `groups.invite_code` is a 12-hex random string generated by default (`00001:78`); it is never rotated and there is no UI to regenerate it.
- `groups.settings JSONB` and `groups.timezone` exist (`00001:75-77`) but no UI writes them (timezone is only editable indirectly through the recurring pattern, which has its **own** `timezone` column).

### 0.2 How roles are assigned / changed
| Event | Where | Resulting role |
|---|---|---|
| Create group | `create_group_with_admin` RPC (`00004_functions.sql:263-306`) called from `src/app/api/groups/route.ts:61-69` | creator → `admin`; also inserts default `notification_settings` |
| Join via invite page | `src/app/invite/[code]/join-button.tsx:47-53` — a **direct client INSERT** into `group_memberships` with `role: 'member'` (the `join_group_via_invite` RPC is *not* used here) | `member` |
| Join from public match page | `join_group_via_invite` RPC (`00004:313-353`) called from `src/app/m/[matchId]/public-match-actions.tsx:194-197` | `member` |
| Change role | `src/app/(dashboard)/groups/[groupSlug]/settings/members-manager.tsx:35-54` — direct client `UPDATE group_memberships SET role` | any of the three |
| Remove member | `members-manager.tsx:56-79` — direct client `UPDATE ... SET is_active = false` (soft delete) | row kept, inactive |

There is **no** SQL function for role changes; everything relies on the RLS policy `"Admins can update memberships" ... USING (is_group_admin(group_id))` (`00003_rls_policies.sql:154-156`). That policy has no `WITH CHECK` and no column restriction, so an admin can also rewrite `group_id`/`player_id` of any membership row of their group.

### 0.3 What each role can do (DB truth, not UI intent)
Helpers: `is_group_member`, `is_group_admin`, `is_group_admin_or_captain` (`00003:36-77`) all require `is_active = TRUE`.

| Capability | member | captain | admin | Enforced by |
|---|---|---|---|---|
| Read group, memberships, matches, signups, teams, rules, notification settings, recurring pattern | yes | yes | yes | `is_group_member` policies |
| Update group settings (name, defaults) | no | no | yes | `00003:135-137` |
| **Delete group** | no | no | **no** — there is no `DELETE` policy on `groups` anywhere in the migrations | see §6 |
| Insert membership | self only (see §0.4) | self only | any | `00003:147-152` |
| Update/delete memberships (roles, removal) | no | no | yes | `00003:154-160` |
| Create match (direct INSERT) | no | **no** | yes | `"Admins can create matches" WITH CHECK (is_group_admin)` `00003:170-172` |
| Update match / set status / add-remove guests / finalize results | no | yes | yes | `00003:174-176`, RPCs in `00007` (`is_group_admin_or_captain`) |
| Manage teams / assignments | no | yes | yes | `00003:231-262` |
| Manage guest_players rows directly | no | no | yes | `00003:346-348` |
| Manage rules | (00008 rewrote) | — | — | out of scope |
| Manage notification settings | no | no | yes | `00003:358-360` |
| Manage recurring pattern | no | no | yes | `00010_recurring_matches.sql:73-77` |
| Update own player profile | own row only | | | `00003:111-113` |

UI copy in `members-manager.tsx:211-215` says "**Capitán:** Puede crear partidos y armar equipos", and the group page shows "Crear partido" to captains (`page.tsx:247-254`; `matches/new/page.tsx:55` also lets captains through) — but the matches INSERT policy is admin-only and `create-match-form.tsx:48-49` inserts directly, so a captain's "Crear partido" fails with an RLS error. Spec §4.2 says captains only "manage teams for a match", so the DB matches the spec and the UI/copy overreach. (Cross-area: match creation belongs to another track; flagged here because the role copy lives in this area.)

### 0.4 Security holes in the role model (critical)
1. **Any authenticated user can insert themselves into any group with any role, including `admin`.** Policy `"Admins can insert memberships"` (`00003:147-152`):
   ```sql
   WITH CHECK (is_group_admin(group_id) OR
       (SELECT pp.id FROM public.player_profiles pp WHERE pp.user_id = auth.uid()) = player_id)
   ```
   The self-join branch does not constrain `role` nor require an invite code. `INSERT INTO group_memberships (group_id, player_id, role) VALUES ('<any group>', '<me>', 'admin')` passes.
2. **All groups (including `invite_code`) are readable by everyone, including `anon`.** Policy `"Anyone can read group by invite code" ... USING (TRUE)` (`00003:125-127`) applies to the whole table for SELECT. Group ids and invite codes are therefore enumerable, which makes hole #1 trivially exploitable and also lets anyone join any group through the normal invite path. This policy is no longer needed: the invite page now reads through the SECURITY DEFINER RPC `get_public_group_by_invite` (`00016_public_group_invite.sql`).
3. **Anyone can insert badges for anyone**: `"System can insert badges" ... WITH CHECK (TRUE)` and `"Anyone can read badges" USING (TRUE)` (`00003:366-372`). Badges are awarded by SECURITY DEFINER functions, so no client INSERT policy is needed at all.
4. Last-admin protection is UI-only (`members-manager.tsx:148`, `:182`). Nothing in SQL prevents a group from ending up with zero admins (two admins demoting each other, or an admin "Hacer miembro" on the other admin then losing their own session; or via hole #1 tooling).

## 5. Leaving a group / removal — precise behaviour

- **There is no "leave group" feature.** No UI (`grep -i "leave|abandonar|salir del grupo"` only hits match signup strings), no RPC, and RLS forbids a member from updating their own membership row (`00003:154-160` admin-only UPDATE/DELETE). The only exit is an admin using "Eliminar del grupo".
- Admin removal = `is_active = false` (soft). Consequences:
  - The row keeps `role` (a removed admin stays `role='admin'`, inactive) — if ever reactivated they come back as admin.
  - `is_group_member()` returns false → the user loses read access to the group, its matches, signups, etc.; the group disappears from their dashboard; `get_unread_notification_count` excludes the group (`00012:305`).
  - Their **profile row and all stats are untouched** (global counters). Badges untouched.
  - Their **existing signups stay as they are** — a `confirmed` signup on next Monday's match still counts against `max_players` and still shows in the list; they cannot cancel (no access). Admin must remove them with `admin_remove_signup`. Nothing prompts the admin to do so.
  - Ratings/votes they cast remain.
  - They cannot rejoin (§Feature: Invite — rejoin bug).
- Hard delete of a membership row (admin DELETE policy exists but no UI) would not cascade to signups either.
- Account deletion: `users.id → auth.users ON DELETE CASCADE`, `player_profiles.user_id ON DELETE SET NULL` (`00001:24,39`) — the profile and its stats/memberships would survive as an orphan "ghost member" still listed in the group (memberships reference the profile, not the user). No UI exists for this anyway.

## 6. Group deletion — precise behaviour

See the Danger-zone UC: currently a no-op because no `DELETE` policy exists on `groups`; UI reports nothing and navigates away. Cascade map documented there; profile stats and badges would survive.

## 7. How profile numbers are computed (SQL truth)

### 7.1 `matches_played`, `goals`, `assists`, `clean_sheets`
`finalize_match_results(p_match_id)` (`00011_post_match.sql:186-302`, wrapped by `admin_finalize_match_results` `00013:66-83`, callable by admin/captain of the match's group): runs once per match (`results_finalized` guard). `matches_played +1` for every `match_signups.status='confirmed'` with a `player_id` (guests excluded, `did_not_show` excluded); `goals`/`assists` from `match_events` (`event_type` goal/assist, `player_id` not null); `clean_sheets +1` for `team_assignments.position='GK'` on a team whose opponent's `teams.score = 0`. Re-finalizing only refreshes scores and re-runs badges — stat counters are never corrected if events are edited afterwards.

### 7.2 `overall_rating` ("Rating")
`player_profiles.overall_rating` defaults to 3.00 (`00001:48`). `update_player_rating(p)` (`00004:184-201`) sets it to `AVG(match_ratings.rating)` over **all** ratings ever received (all groups, all time — no recency weighting, so "recent form" from spec §4.7 does not exist). It is only invoked from `finalize_match_results` for players who already have a rating *in that match* at finalize time (`00011:289-294`). Ratings submitted afterwards (the normal case: results are entered, then people vote during the 7-day window) **never update `overall_rating`** because finalize runs once. Seed data compensates by calling `update_player_rating` for everyone (`seed.sql` line ~292). Guests use `guest_players.estimated_rating` (not shown in this area).

### 7.3 `reliability_score` ("Confiabilidad")
`update_player_reliability(p)` (`00004:144-177`): over **all** the player's signups (all groups, lifetime): `score = 1 − 0.05 × late_cancels − 0.15 × no_shows`, clamped to [0,1], where late cancel = `status='cancelled' AND cancel_time > match.date_time − 6h`, no-show = `status='did_not_show'`. Called from `finalize_match_results` (for all signups of that match, `00011:281-284`) and from `admin_set_signup_status` (`00014:66-68`). `cancel_my_signup` (`00007:180`) does **not** call it, so a late cancel only lowers the score when that match is later finalized. There is no decay, no recovery for attending, no per-group view; the displayed number is cumulative-lifetime. `v_total_signups`/`v_confirmed_played` are computed but unused (`00004:153-166`).

### 7.4 `mvp_count` ("MVPs")
Trigger `match_mvp_votes_recompute` (AFTER INSERT/DELETE on `match_mvp_votes`, `00011:73-90`) → `recompute_match_mvp` (`00011:26-67`): top-voted candidate, tie → earliest first vote; reconciles `matches.mvp_player_id` and `mvp_count` (decrement old holder floor 0, increment new), and inserts/deletes the `mvp` badge for that match. Votes allowed only for confirmed players of a `finished` match within 7 days (`00011:338-352`). MVP can flip back and forth as votes come in; the profile shows live counts.

### 7.5 Badges ("Insignias")
`award_badges_for_match` (`00011:101-177`), called at the end of `finalize_match_results` (also on the re-finalize path): `hat_trick` (≥3 goals in the match), `playmaker` (≥2 assists), `safe_hands` (GK on a team whose opponent scored 0), `ironman` (confirmed at each of the group's 10 most recent finished matches incl. this one; only once the group has ≥10 finished matches; re-awarded every qualifying match since `match_id` differs). `mvp` from §7.4. `UNIQUE(player_id, badge_type, match_id)` gives idempotency. No `first_match`, `mvp_streak` (labels exist in UI only). Guests never get badges (`player_id IS NOT NULL` filters).

### 7.6 Derived on the page
"Rating promedio recibido" = live `AVG(match_ratings.rating)` for the player, all matches (`players/[playerId]/page.tsx:153-160`); "Goles por partido" = `goals / matches_played`.
